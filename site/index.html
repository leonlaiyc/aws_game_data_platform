01 / 07

THE OPERATING REALITY

先有營運問題，才有架構。

這些不是為了套 AWS 服務而整理出的抽象需求，而是會反覆消耗分析、營運、客服與工程資源的工作情境。

M1 異常／套利

沒有主動監控，只能被動發現。

數據缺乏主動監控；一旦留存或營收下滑，通常要等到人為發現才會開始處理，存在時間落差，也讓團隊只能被動應對。另外，當詐欺玩家採用未曾遇過的套利手法時，也很難只靠既有規則識別。

CORE PRIORITY
M2 實驗運營

並行實驗的狀態存在每個人的腦中。

不同遊戲的 A/B testing 同時進行時，沒有中央化方式查看並行實驗狀態，得一個一個問人，或等到站會才知道。

這個核心問題同時還伴隨兩個次要、但會持續增加營運成本的問題：

  • SRM、guardrail 依賴人工抽查，異常實驗停止有延遲。
  • 相同 data feature 因為由不同組員負責而重複開發。
M3 臨時分析

Dashboard 回答不了突然出現的「為什麼」。

Dashboard 可以回答固定問題，但當老闆、業務或客戶突然詢問「今天營收為什麼掉了？」時，現有 dashboard 往往無法直接回答。

這類提問通常伴隨急迫性，又會在不可預期的時間出現，進一步加重分析人員的工作負擔；當客戶數量增加，問題頻率也會隨之上升。

M4 合作夥伴支援

重複問題一路升級到工程師。

不同時區的合作夥伴經常反覆詢問類似的產品對接與整合問題：一方面客服需要重複回答；另一方面，若客服無法處理，問題就會升級到工程師層面，進一步增加開發負擔。

03 / 07

SYSTEM OWNS REPETITION · PEOPLE OWN JUDGEMENT

四個工作流，改變四種人的工作方式。

每張卡只回答：原本怎麼做、系統接手什麼、人保留什麼決策，以及目前真正的實作邊界。

01
M1 · DETECTION

異常與套利偵測

原本怎麼做

依賴人主動查看報表，發現下滑後才開始追查；套利調查依賴既有經驗。

系統接手

定期檢查 DAU、GGR、成熟 cohort 留存，並輸出 threshold、baseline 與風險證據。

人保留決策

判斷根因、採取營運處置；套利結果只進入人工風險審查。

實作邊界

套利目前是規則式，只識別已定義的雙訊號模式，不宣稱能抓未知手法。

02
M3 · NL ANALYTICS

Analytics NL Assistant

原本怎麼做

突發的 what／why 問題打斷分析師，還要重新查基線、遊戲別與共變動。

系統接手

允許清單 SQL 回答 what；first-look 與 diagnose 組合證據回答 why；答不了就建 ticket。

人保留決策

判讀營運脈絡、確認根因，並決定後續處置。

實作邊界

只支援受治理的 KPI 與查詢模板；沒有 free-form text-to-SQL，也不支援未治理的 country／player 維度。

03
M2 · EXPERIMENT OPS

實驗運營平台

CORE PRIORITY
原本怎麼做

並行實驗狀態散落在人與站會中；SRM、guardrail 靠人工抽查，共用 feature 重複開發。

系統接手

中央 registry、IAM-derived owner、SRM、guardrail、allocation kill switch 與共享 feature registry。

人保留決策

決定假設、指標、是否採納結果，以及異常實驗後的產品處置。

實作邊界

監控 cadence 最差為一小時；目前是本機簽名 console，尚未提供 hosted SSO team UI。

04
M4 · PARTNER SUPPORT

合作夥伴支援 Chatbot

原本怎麼做

客服重複回答整合問題；無法處理時再把缺乏脈絡的問題轉給工程師。

系統接手

依身份選擇 provider／operator 語料，先澄清，再回答或建立可追蹤的 escalation。

人保留決策

處理文件無法回答、需要產品判斷或真正涉及工程變更的案件。

實作邊界

使用模擬 IAM 身份與小型語料；partner IdP、CRM delivery、時區 profile 尚未 production-ready。

05 / 07

          

            
NOT NOW — AND WHAT WOULD CHANGE THE DECISION

            
不逐項背服務；只談三類判準。

            

              每一類 trade-off 都回答同一件事：現在為什麼不需要，以及什麼可量測條件會讓答案翻轉。
            

          

        


        

          

            01
            
WORKLOAD ECONOMICS

            
目前的使用頻率，值得支付常駐成本嗎？

            
Redshift / EMR · persistent Kinesis

            

              NOW
              
資料量小、查詢間歇；預設採用 request-priced 或 scale-to-zero 元件，Kinesis 只做短生命週期示範。

            

            

              DECISION FLIPS WHEN
              
出現持續查詢併發、穩定高流量，或 sub-minute SLA 成為正式需求。

            

          


          

            02
            
DATA ACCESS PATTERN

            
真的需要線上低延遲 serving 或大規模 retrieval 嗎？

            
SageMaker Feature Store · OpenSearch / vector store

            

              NOW
              
Feature 用於 batch analysis；合作夥伴 corpus 小且可受控放入 context，現階段不需要新增 serving 與 retrieval 平面。

            

            

              DECISION FLIPS WHEN
              
Feature 需要毫秒級線上查詢，或文件量超出 in-context 方法可治理的範圍。

            

          


          

            03
            
MANAGED WORKFLOW VS CONTROL

            
應該購買完整工作流，還是保留較窄但可驗證的控制？

            
Amazon Quick · Amazon Q Business · direct Bedrock

            

              NOW
              
PoC 使用窄範圍自訂流程，展示 SQL allowlist、數字所有權、tenant scope 與 disclosure control。

            

            

              DECISION FLIPS WHEN
              
真實團隊需要完整 BI、自助報表、企業搜尋、內容維護與使用者管理，managed workflow 的組織價值開始更高。

            

          

        

      


      

        

          

            
06 / 07

            

              
THREE IMPLEMENTATION TRAPS

              
不是心得，而是測試後真的改了設計。

              

                這些問題是在建置與驗證這個 PoC 時發現，不是宣稱來自 production incident。
              

            

          


          

            

              
01AWS

              

                
看得到 row filter，不代表租戶真的被隔離。

                

                  I ASSUMED
                  
建立 Lake Formation row-level filter 後，各 tenant 就只能看到自己的資料。

                

                

                  IAM_ALLOWED_PRINCIPALS
                  

                    Glue table 的向下相容 grant 仍可能把權限交回 IAM，讓 filter 看起來存在、實際卻是 no-op；直接 S3 GetObject 也是另一條繞過路徑。
                  

                

                

                  DESIGN CHANGED
                  

                    撤銷該表的 compatibility grant、移除 analyst 的直接 S3 data access，再同時驗證 Athena 只看得到自己的 site，且 GetObject 必須被拒。
                  

                

                
租戶隔離只有在繞過路徑也失敗時才是真的。

              

            


            

              
02DATA

              

                
同一場異常，第一天會響，第三天可能不再響。

                

                  I ASSUMED
                  
只要 DAU 持續低迷，EWMA detector 就會持續認為它異常。

                

                

                  

                    2026-06-10 · DAY 1
                    DAU 91 vs baseline 204
                    約 3.9σ → ALERT
                  

                  →
                  

                    2026-06-12 · DAY 3
                    2 個低迷日已進入 window
                    baseline 下移、標準差擴大 → NO ALERT
                  

                

                

                  DESIGN CHANGED
                  

                    將目前 detector 明確定義為 onset detection：負責盡早觸發第一次調查，不假裝它同時管理持續事件狀態；production 若要持續告警，需另保留不會適應的 reference baseline。
                  

                

                
偵測「事件開始」與追蹤「事件仍在發生」是兩個不同問題。

              

            


            

              
03AI

              

                
Prompt 說不能洩漏，模型仍然洩漏了。

                

                  I ASSUMED
                  
明確要求模型不得顯示內部文件名稱與 ID，就足以保護對外回答。

                

                

                  MODEL OUTPUT · INTERNAL AUDIT ONLY
                  “Document ID: [internal identifier]”
                  validation: internal_identifier_leak · fallback: true
                

                

                  DESIGN CHANGED
                  

                    在送給合作夥伴前，由 deterministic validator 檢查並替換不安全輸出；完整證據只保留在內部 audit path。
                  

                

                
Prompt 是要求；code validator 才是 enforcement boundary。
